# Plan 01-03: Bounding Logic — Tool Exclusion, Markers, and Plateau

<objective>
Implement the core bounding behavior: exclude tool transcript from turns outside the hot window, inject synthetic marker messages at exclusion boundaries so the model knows content was removed, and wire transform metadata to the snapshot for observability. After this plan, prompt size plateaus instead of growing linearly with conversation length.

Purpose: This is the primary deliverable of Phase 1 — the prompt size plateau. Depends on config knobs (Plan 01) and observability types (Plan 02).
Output: Tool exclusion in transformMessages, marker messages, snapshot wiring, plateau-proving tests.
</objective>

<must_haves>
- Turns outside the hot window have tool_use and tool_result content blocks removed (not just summarized — fully excluded)
- Excluded content is replaced by a synthetic marker message: `{ role: "assistant", content: "[context-assembler:excluded] N tool calls removed from turn T — set assembler.hotWindowTurns to adjust" }`
- Hot window turns (most recent N per `hotWindowTurns` setting) are never excluded
- TransformMetadata is populated with per-turn decisions including action and reason
- TransformMetadata is passed to captureEffectivePromptSnapshot in sdk.ts
- Tests prove: (a) tool content excluded outside hot window, (b) markers injected, (c) hot window content preserved, (d) token count does not grow linearly with turn count
- `bun check` passes
</must_haves>

<action>
In `packages/coding-agent/src/context/assembler/message-transform.ts`, enhance the `transformMessages()` function:

**Step A: Identify hot window boundary**

At the start of `transformMessages`, compute the hot window boundary:
```typescript
const hotWindowTurns = options.hotWindowTurns ?? DEFAULT_HOT_WINDOW_TURNS;
// Turns are grouped as user+assistant pairs. Count from the end.
// The last `hotWindowTurns` turn pairs are in the hot window.
```

Determine which turn indices are in the hot window (the most recent `hotWindowTurns` turn-pairs). Turn pairs = consecutive (user, assistant) message groups.

**Step B: Exclude tool transcript from cold turns**

For turns OUTSIDE the hot window, iterate their content blocks and remove:
- `tool_use` content blocks (from assistant messages)
- `tool_result` content blocks (from user messages that follow tool_use)

These are the tool transcript. Text content blocks in assistant messages SHOULD be preserved (the model's reasoning text is still useful context).

For each excluded turn, create a `TurnDecision` with:
- `action: "exclude"` (or `"stub"` if partial exclusion)
- `reason: "tool-transcript-outside-hot-window"`
- Populate `inputTokens` and `outputTokens` with the token count of the removed content (use the existing token counting mechanism in the file — look for how tokens are counted in the current stubbing logic)

**Step C: Populate TransformMetadata aggregates**

After processing all turns, compute and set:
```typescript
metadata.keptCount = decisions.filter(d => d.action === "keep").length;
metadata.stubbedCount = decisions.filter(d => d.action === "stub").length;
metadata.excludedCount = decisions.filter(d => d.action === "exclude").length;
metadata.totalInputTokens = /* sum of inputTokens from all decisions */;
metadata.totalOutputTokens = /* sum of outputTokens from all decisions */;
metadata.budgetUsedTokens = /* total tokens in the final message array */;
metadata.budgetMaxTokens = options.maxTotalTokens ?? /* default */;
```

**Important:** Do NOT break existing stubbing logic for non-tool content. The existing summary/stub logic for old turns may still apply to text content. Tool exclusion is additive — it removes tool_use/tool_result blocks that the existing logic may have been passing through.

Look at how content blocks are identified — Anthropic message format uses `content: Array<{ type: "text" | "tool_use" | "tool_result", ... }>`. Filter by `type`.
</action>

<task id="2" title="Inject synthetic marker messages at exclusion boundaries">
<read_first>
- packages/coding-agent/src/context/assembler/message-transform.ts (the exclusion logic from task 1 — understand where turns are removed and where markers should be inserted)
- packages/coding-agent/src/context/assembler/types.ts (message types used in the codebase)
</read_first>
<action>
In `packages/coding-agent/src/context/assembler/message-transform.ts`:

**Step A: Define marker message format**

After excluding tool transcript from a turn (or group of consecutive excluded turns), inject a synthetic assistant message at the boundary:

```typescript
{
  role: "assistant",
  content: `[context-assembler:excluded] ${excludedToolCallCount} tool calls removed from ${excludedTurnCount > 1 ? `turns ${startTurn}-${endTurn}` : `turn ${startTurn}`} — set assembler.hotWindowTurns to adjust`
}
```

The marker should:
- Use `role: "assistant"` so it doesn't break the user/assistant alternation requirement
- Include the count of removed tool calls (not just turns)
- Include which turns were affected
- Include actionable guidance (the setting name to change)

**Step B: Consolidate consecutive exclusion markers**

If multiple consecutive turns have tool transcript excluded, emit ONE marker for the entire range, not one per turn. This keeps the prompt clean.

**Step C: Place markers correctly**

Insert the marker message where the excluded content was, maintaining message order. The marker replaces the tool blocks — text blocks from the same turn should appear before or after the marker as appropriate.

If a turn has ALL its content excluded (it was purely tool calls with no text), the entire turn's messages are replaced by the single marker. If a turn has mixed content (text + tool calls), keep the text, remove the tool blocks, and append a shorter marker noting the tool exclusion.

Mixed content marker: `[context-assembler:excluded] ${count} tool calls removed from this turn`

**Important:** Ensure the final message array still alternates correctly (user, assistant, user, assistant). Markers being assistant role helps. Verify no two consecutive assistant messages exist after injection.
</action>

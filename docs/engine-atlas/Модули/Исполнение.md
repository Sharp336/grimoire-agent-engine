# Исполнение

Принимает запуск, продолжает работу и обрабатывает отмену.

**EngineRuntime**

---

## Как работает

Команды приходят через control-query, hosted bridge и NATS adapter. Runtime создаёт AgentSession, открывает историю и фиксирует состояние исполнения.

### S1: точная привязка и владелец установки

Runtime contract revision 16 передаёт `bindingSnapshot`: `agentInstanceRef`, nullable `taskRef` и `workStepId`, `bindingRevision`, nullable `installationId`, `parentAgentInstanceRef`, `parentAttemptId` и `parentBindingRevision`. Core/ClientHost фиксирует этот объект при допуске Start. Engine сохраняет его в идентичности команды, Attempt и привязке сессии. Повтор commandId с другим snapshot конфликтует. Текущая Task не выводится из Agent URI; старый URI остаётся непрозрачной историей создания.

Legacy Agent навсегда сохраняет project-привязку revision 0 и installation null. S1 допускает born-owned Agent с revision ≥1, owner-scoped URI и точным `install_<32hex>`, включая standalone и unbound. Перед owned admission ClientHost проверяет локальный WinCred marker и вызывает `installation.verify` с principal/device/engine и точным runtime16 hash. Latch сбрасывается при каждом запуске Engine; секрет в Engine не передаётся. Новый r1 Agent получает OPEN gate при первом точном Start. Отсутствующий gate при уже сохранённой Agent identity не восстанавливается автоматически. Независимый native SDK без hosted AgentRef не получает Task-привязку. JSON runtime16 остаётся побайтно прежним.

Переиспользование live/native сессии, перенос контекста, восстановление workspace и доступ к дочерней истории проверяют semantic tuple отдельно от прежних profile/conversation digest. Формулы digest не меняются. Для старой записи допустимо доказательство неизменяемой legacy-привязки из точной сохранённой команды и канонического r0 snapshot; неизвестная история не восстанавливается из URI. Изменённый cwd сохраняет Agent, но создаёт свежую сессию; пропущенный cwd до допуска нормализует ClientHost из предыдущего запуска.

Resume и context/history/holds читают точный Attempt. Дочерний Start наследует Task/WorkStep и parent revision из допуска родителя; offline child не выбирает другую WorkStep без авторитетной проверки принадлежности. Исторические события и результаты сохраняют snapshot своего Attempt, а не текущую Task родителя.

После semantic adoption текущие summary/nativeTarget больше не выбирают Attempt предыдущего binding revision: до первого нового Start Agent имеет registered target без attemptId. UI отправляет launch, а не continue старого Attempt. Явное чтение исторического Attempt по его ID сохраняет прежний snapshot и историю.

Повтор pre-S0 дочернего запуска сохраняет исходную сериализованную команду и canonical hash. Новые поля не дописываются под прежним commandId. Проверенное дополнение привязки передаётся отдельно от идентичности команды. Для старой дочерней истории используются сохранённые parentAttemptId/toolCallId/WorkStep и точная неизменяемая r0-привязка родителя. Hosted-проекция отложенного события может получить её из канонической owner-checked `legacy_immutable` записи родителя; URI служит только проверкой вычисленного birth ID, не источником Task.

Сохранённая команда проходит тот же envelope-validator, что и Control Query; отсутствие S0 snapshot допустимо только для уже сохранённой legacy-команды. Текущие `engineGeneration` и `issuedAt` назначаются исключительно новой команде. При изменении метаданных терминального Attempt транзакция по-прежнему обязана читать и проверять `metadata/effects:<attemptId>:<bindingId>`: нулевое число открытых effects не заменяет revision predicate.

Start с неверным поколением обычно получает атомарный отказ. Исключение — сохранённый owned Start без созданного Attempt: проверенные установка и текущий semantic snapshot позволяют текущему processor повторно принять исходную команду, не меняя её canonical hash, command/execution/Attempt ID или snapshot. Закрытый binding gate возвращает retryable `binding_pending`; NATS делает NACK без терминального receipt и без расходования execution retry budget. Реально работавший Attempt после потери Engine по-прежнему завершается через обычное crash settlement.

Повтор уже ожидающего Start (`binding_pending:true`, `processor_generation:null`) не записывает прежнюю строку и не публикует change signal. Если processor ранее захватил Start, закрытие gate освобождает этот claim одной записью; последующие повторы остаются read-only. Поэтому ожидающие дочерние Starts не будят друг друга бесконечно.

Повтор commandId с другим payload отклоняется без изменения исходной идентичности, receipt, состояния или binding snapshot Attempt. NATS завершает эту доставку через `term` и передаёт исходный `EngineCommandConflictError` в `onError` (`reason: canonical_content`). Это report-only audit: он не создаёт `command.rejected` или другое событие исходного запуска, поскольку Hosted Bridge связывает `command.rejected` с исходной job и терминально завершает её. Гонка settlement с тем же canonical hash и другим receipt имеет отдельную причину `receipt`; она тоже завершает доставку через `term`, сохраняет выигравший receipt и не проходит admission-audit. Ошибка обработчика `onError` не отменяет `term` и не подавляется. Коллизия другого principal/Agent не дописывает событие в чужую историю.

Managed ClientHost передаёт фактический package sequence через `omp engine serve --installed-sequence <int>`. Engine пересылает его в `X-Grimoire-Client-Installed-Sequence`, а feature carrier — JSON-массив `["grimoire.task.v4","agent_binding.v1"]` в `X-Grimoire-Client-Features`. B1 sequence 188 следует за B0 187; обязательный floor проверяет Core, а не совпадение runtime hash. Отсутствующий sequence не заменяется вымышленным значением.

Control Query использует существующий локальный authenticated transport: `binding.prepare {gate}`, `binding.census {agentInstanceRef,installationId,operationId,proposalHash,bindingRevision}`, `binding.adopt {gate,result}`, `binding.activate {result}`, `binding.abort {result}`. В Rocks metadata сохраняется semantic gate отдельно от manual hold. Prepare закрывает старую привязку; adopt сохраняет `committed_closed` и новый `committedTarget`, освобождает idle live session; только канонический adopted result открывает новый revision. Abort разрешён только для точного старого revision с каноническим aborted result. Ни рестарт, ни logout, timeout, pause или release gate не открывают.

Storage protocol20 хранит binding metadata в явных subtype-конвертах: `semantic_binding` для gate, birth и census; `binding_result` для результатов операций; `binding_mutation` для revision marker. Gate внутри конверта сохраняет исходную runtime16-форму без добавленных полей. Legacy summary не читает semantic gate: неизменяемый legacy URI исключает owned-привязку и сохраняет прежний бюджет атомарного branch control.

Терминальные результаты сохраняются отдельно для каждого operationId и action, вместе с точной исходной привязкой и возвращённым gate. Prepare/abort A, затем prepare/abort B не стирают результат A: поздний повтор A возвращает свой сохранённый результат без изменения текущего gate. Повтор старого adopt не освобождает здоровую live session другой операции.

Сравнение replay использует стабильные поля результата операции: Agent, installation, operation/proposal, status/phase, canonical revision, binding revision и Task/WorkStep; transport `action` не участвует. Поэтому commit → status/prepare, а также adopted/aborted → status/prepare возвращают сохранённый gate. ClientHost передаёт Engine нормализованный immutable `operation_result`; изменённый стабильный результат получает `stale_target`.

После hosted commit ClientHost остаётся `committed_closed`. Если Engine adopt возвращает retryable `binding_pending`, ClientHost продолжает ограниченные страницы `binding.census` той же операции со старым bindingSnapshot и повторяет adopt только после полного свежего нулевого census. Engine сохраняет canonical commitment до отказа, оставляя preparing gate закрытым; другая цель или abort уже не допускаются. После adopt census использует новый binding revision; activate проверяет тот же полный нулевой cut и при инвалидации требует повторной сертификации, не открывая gate. Отложенный adopted result также сохраняется как стабильный fence. Рестарт требует новой проверки установки и census текущего поколения.

`next_cursor` отражает gate/marker/generation и полный сохранённый обход, поэтому меняется при каждой странице с прогрессом. Cursor не передаётся назад: следующий идентичный запрос продолжает durable scan. Busy, unknown, неполная ancestry или ненулевые счётчики не разрешают ни adopt, ни activate.

При завершении record-page поле `after` удаляется из frame до перехода к обходу детей. Отсутствующая граница не сериализуется как `undefined`: canonical cursor и durable stack используют одну JSON-совместимую форму, включая пустой Agent и возобновление после перезапуска.

Peer mailbox обрабатывает `EngineBindingPendingError` отдельным NAK без ack/term. Budget `commandAttempts` считает реальные ошибки доставки текущего adapter, а не broker redelivery count; ожидание prepare или проверки установки после рестарта не расходует его. Poison и target errors остаются терминальными.

Census читает только `agent_records` целевого Agent и его потомков, перечисленных через `identity_parent`, и сохраняет depth-first курсор в Rocks. Одна страница содержит до 25 runtime rows либо одного ребёнка; эти чтения не накапливаются в atomic checks. В транзакции страницы остаются только gate, checkpoint и marker. Посторонние identity-less события не участвуют в census; нарушенная обязательная ancestry найденного потомка блокирует подтверждение. Повтор запроса продолжает сканирование; `unknown` и ненулевой `next_cursor` не означают idle.

Storage предоставляет `indexRevision` для короткого снимка раздела и инвалидирует cursor при его изменении, но write protocol не принимает index revision checks. Read-only проверка разделов сама по себе не закрывает гонку между последним чтением и commit/adopt. Поэтому используется один checked marker на изменённое owned-дерево: обычный `put` читает его revision, owner проверяет его вместе со всей мутацией и атомарно увеличивает revision. Unchecked puts отсутствуют. Общий механизм повторяет conflict не более четырёх попыток; исчерпание бюджета завершает всю мутацию ошибкой, а не пропускает marker. Один дополнительный checked record на дерево учитывается в существующем лимите 100, без увеличения лимита или per-Agent ancestry/gate reads.

Marker меняют только изменения наблюдений census: membership/ancestry, наличие полученных commands, нетерминальных Attempts, открытых effects, pending inbox, обычных событий и успешных hosted-binding delivery receipts; semantic gate также инвалидирует cut. Publication timestamps, projections, delivery retry bookkeeping, другие sinks и повтор прежнего состояния marker не меняют. Legacy-дерево без gate marker не пишет. Census сравнивает revision до и после страницы и включает его в atomic checks; adopt проверяет тот же revision. Внутри одного owned-дерева общий marker консервативно инвалидирует census соседних ветвей и может вызвать bounded CAS retry; отдельные деревья не конкурируют за marker. Pending hosted-проекция учитывается до подтверждения Hosted Bridge, не только до публикации NATS. В preparing checkpoint относится к старому r; в committed_closed — к committedTarget r. Для commit/adopt допустим только полный нулевой census.

Hosted Bridge отправляет событие и затем сохраняет delivery receipt. Для уже удалённого локального чата receipt остаётся `delivered`, но не содержит `agent_instance_id`: состояние удаления читается из authoritative identity в той же checked-транзакции. Поэтому owner не отклоняет позднее подтверждение как runtime-запись удалённого чата, а новый receipt не создаёт census marker. Для живого owned-чата сохраняются agent tag и точная инвалидация cut; повтор доставки сохраняет прежний ключ и состояние receipt.

Hosted Bridge раздельно опрашивает legacy и installation-scoped очереди. Каждый hosted Start сначала проходит CH `localize_start` по точным job/lease/command. Immutable mismatch даёт durable отказ; временная недоступность CH/cache и binding wait сохраняют нетерминальный запуск через `release_delivery`. Профиль, вход, snapshot и occurrence IDs не подменяются при локализации. Same-installation rebind не переносит transcript, provider/native handle, inbox или дочернюю историю в новую Task. Cross-device transfer, takeover, TTL recovery и защита от украденного bearer не входят в S1.

Owned child может быть зарегистрирован через enrollChild до первого Start. При r=1 admission атомарно создаёт provisional semantic gate только для точных child identity, owner и parent provenance, подтверждённых сохранённым родительским Attempt и открытым текущим parent gate, при отсутствии binding и Attempts ребёнка. Отдельная durable запись рождения запрещает заново создавать потерянный established gate. Это общий путь local и hosted children. Неизменённая owned-привязка `taskRef:null` сохраняет прямую дочернюю историю при совпадении revision, provenance и cwd; отсутствие Task само по себе не сбрасывает доступ к истории.

Отмена дочернего запуска адресует точные command/execution/Attempt IDs. Пока binding закрыт и Attempt ещё не создан, отмена атомарно сохраняет rejected receipt `cancelled`, освобождает pending budget и будит ожидающих результат. Поздний повтор команды читает receipt и не запускается. Listener отмены `waitAttemptResult` установлен до первого асинхронного чтения и снимается при любом выходе; no-op admission не используется как источник пробуждения.

Явная смена cwd того же Agent создаёт свежий native/provider context. Если session defaults содержат read-only Settings прежней папки и профиль не дал новый snapshot, Engine клонирует Settings для новой папки: перечитывает её project scope, сохраняет явно заданные overrides и не мутирует прежний snapshot. Native header и Settings получают новый cwd. Отсутствующий cwd по-прежнему наследует сохранённую папку; исходный Start с чужим settings cwd остаётся ошибкой.


## Долговечный приём очереди

`EngineRuntime.#startInLane` сначала атомарно принимает Start и lease, сохраняя неизменяемый receipt `applied`. Это ещё не подтверждение доставки сообщения. Проверка материала исполнения, вложений и принадлежности сессии предшествует приёму native user entry. Промежуточный checkpoint заголовка сохраняет locator, но не переносит pending inbox.

После однократного добавления command context внутренний `AgentSession.acceptEngineQueuedInput` сохраняет и flush-ит вход без запуска модели. Затем одна транзакция фиксирует checkpoint, перенос очереди и ACK с исходными mutation ID и expected revision. `resume_queued` продолжает native history без второго prompt; повтор Start сообщает потребление только при фактическом ACK этим Attempt.

Ошибка до ACK оставляет сообщение pending в исходной сессии и revision. Если native entry уже сохранён, перезапуск не воспроизводит его автоматически: нужен явный Continue. Восстановление сверяет исходный Start по Agent, principal, semantic binding, queue ID и revision, требует терминальный прежний Attempt и единственный entry в загруженном контексте. Сохраняются исходные source command, launch snapshot и user client ID; peer-вход не получает выдуманный client ID. Сохранённый, но не загруженный entry даёт `stale_target`, а отдельные сообщения с одинаковым текстом остаются отдельными входами.

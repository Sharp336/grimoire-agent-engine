# RCA: Near-100% CPU During Routine Session

**Profile**: `~/.omp/reports/omp-report-2026-07-29T00-26-06-868Z.tar.gz`
**Captured**: 2026-07-28, 45.2s window, 23,914 samples
**Verdict**: The TUI **Loader spinner** busy-spins the CPU at ~100% for the entire session, re-running the full text-wrap + line-prepare pipeline every 80 ms even when no tool work is happening. 99.75% of CPU is overhead.

## Root Cause #1 (dominant): Loader spinner re-renders every 80 ms with no content cache

### Mechanism

`Loader` (`packages/tui/src/components/loader.ts:19`) is the spinner shown while a tool/turn is "working". Its `start()` (line 79) sets an interval:

```ts
const intervalMs = this.messageColorFn.animated === true ? RENDER_INTERVAL_MS : SPINNER_ADVANCE_MS;
this.#intervalId = setInterval(() => { ...; this.#updateDisplay(); }, intervalMs);
```

- `SPINNER_ADVANCE_MS = 80` (line 6) — the normal cadence.
- `RENDER_INTERVAL_MS = 1000/30 ≈ 33.3` — when the message colorizer is `animated`.

`#updateDisplay()` (line 118) calls `setText(`${frame} ${message}`)` then `this.#ui.requestDirectWrite(this)`.

**The cache-defeating chain**: `setText` changes the text every tick (the braille glyph advances ⠋→⠙→⠹…), so `Text.setText()` (line 54) returns `true` and **clears `#cachedLines`**. The next `root.render(width)` inside `requestDirectWrite` therefore misses the `Text.render()` cache (line 99) and re-runs the expensive pipeline:

1. `wrapTextWithAnsi(normalizedText, contentWidth)` — **3,250 ms** — re-wraps the *entire message* to terminal width, even though only the 1-cell spinner glyph changed.
2. `visibleWidth(lineWithMargins)` per line — **2,547 ms** — re-measures every wrapped line.
3. Then `TUI.requestDirectWrite` calls `#prepareLine()` per rendered line (`tui.ts:2095`), which runs `normalizeTerminalOutput` + `#ansiAsciiLineWidth` + `visibleWidth` + possibly `truncateToWidth` **again** on each line.

`requestDirectWrite` was hit **1,895 times** in 45 s (≈42/s). The spinner fires ~560 times (45 s / 80 ms); each fire is sampled multiple times because the call is expensive. The `render@2641` child of `requestDirectWrite` alone accounts for **12,792 ms**.

### Why it spins during "routine" idle

The profile shows the Loader render loop active in **every 5-second window** (17–49% of samples), with no idle gap. Only 79 ms of `shell.run` work occurred. The session was in `working` state (the title spinner, which only runs in `working`, was also active), so the Loader stayed mounted and its interval never cleared. The agent runtime keeps the spinner alive across the gaps between and around tool calls; when those gaps are long (LSP indexing, thinking, network waits), the spinner alone pegs a core.

### Prior art

This is the same class of bug as the 2026-07-01 RCA (TUI render-loop busy-spin) and the 2026-07-02/03 residual-overhead fixes (shimmer cache, SSE per-line decode, `requestComponentRender` for timers). The `requestDirectWrite` fast-path was added to *avoid* the full compose/diff pipeline for spinner ticks, but it still re-renders the component and re-prepares every line — the `wrapTextWithAnsi` + `stringWidth` cost was not eliminated, only the diff was.

## Root Cause #2 (secondary): Terminal-title spinner

`title-generator.ts:545` runs a second 80 ms `setInterval` writing OSC 0 title sequences (`\x1B]0;π ⠋ label\x07`) while state is `working`. 1,601 ms (3.5%). It `unref()`s the timer so it doesn't keep the loop alive, but while the loop *is* alive (driven by the Loader) it adds ~36 writes/s of `process.stdout.write`. Lower priority than #1 but redundant work during the same idle gaps.

## Root Cause #3 (background): Stream-I/O pull overhead

7,205 ms (16%) in Bun's native readable-stream pull algorithm (`#getInternalBuffer`, `#pull`, `subarray`, `#onNativeReadableStreamResult`). This is the terminal stdin readable stream being polled continuously. It has no `cli.js` ancestor — it's runtime callback overhead from the event loop processing the timer fires and TTY reads. It scales with how often the loop wakes; reducing the timer cadence (fixing #1) will collapse this too.

## Fix Recommendations

### Fix A — Cache the wrapped message independently of the spinner glyph (eliminates ~51% of CPU)

The spinner glyph and the message are independent: the glyph changes every tick, the message rarely. The Loader's `render()` already caches `#layout` keyed on `#layoutSource` (the `super.render()` output), but `super.render()` (i.e. `Text.render`) misses its cache because `setText` clobbered it with the new glyph.

**Approach**: stop baking the glyph into `Text.text`. Keep the message as the cached text; inject the spinner glyph at render composition time only (it already does this — `render()` prepends `this.spinnerColorFn(frame)` at line 64). The `setText` in `#updateDisplay` should set **only the message**, and a separate flag should mark "frame advanced" so the TUI knows to re-emit the line without re-wrapping.

Concretely:
- `#updateDisplay()` should call `setText(this.message)` (not `${frame} ${message}`); the frame is rendered from `this.#currentFrame` directly in `render()`.
- Only call `requestDirectWrite` when the *message* changed (`textChanged`) **or** the colorizer is animated. The frame-advance case still needs a re-render, but `Text.render()` will hit its cache (text unchanged → wrapped lines reused), and only the cheap glyph-prefix composition runs.
- This turns the per-tick cost from `wrapTextWithAnsi` + `visibleWidth` × N lines → a single string concat + the existing `#prepareLine` (which can itself be skipped when only the glyph changed and the prepared line is structurally identical).

**Expected impact**: eliminates `wrapTextWithAnsi` (3,250 ms) and most `stringWidth` (2,547 ms) from the hot path — ~5.8 s of the 23.3 s render loop, and shrinks the per-tick `render@2641` (12.8 s) to near-zero for frame-only ticks.

### Fix B — Throttle/coalesce `requestDirectWrite` when only the glyph changed

Even with Fix A, calling `requestDirectWrite` 12.5×/s (80 ms) does a component render + per-line `#prepareLine` + terminal write. For a single-row spinner, the write is tiny but the `#prepareLine` per line is not. Two options:

1. **Skip `#prepareLine` on frame-only ticks**: `requestDirectWrite` already compares `previousWindow[i]` to `prepared.line` and computes `firstChanged`/`lastChanged` (`tui.ts:2121`). If the prepared line is identical (only the glyph's ANSI color changed but the visible width is the same), `firstChanged === -1` and it early-returns after a cursor write. The problem is `#prepareLine` *runs* before the comparison. Cache `#preparedMeta` per `(raw, width)` so a frame-only re-render reuses the prepared line.
2. **Gate the cadence on visibility**: 80 ms (12.5 fps) for a braille spinner is fine perceptually, but `requestDirectWrite` could be coalesced with `requestAnimationFrame`-style scheduling so two ticks within the same frame budget (e.g. 16 ms) collapse. The `#nn`/`#e0` throttle already exists for `requestComponentRender`; `requestDirectWrite` bypasses it by design (it's the "direct" path). A lightweight 16 ms min-interval on `requestDirectWrite` would cap it to 60 fps max without perceptual loss.

### Fix C — Stop the title spinner when the Loader is already spinning (eliminates 3.5%)

The title spinner (`title-generator.ts:545`) and the in-TUI Loader spinner animate the same glyph at the same 80 ms cadence while `working`. The title spinner writes an OSC sequence every tick. Either:
- Derive the title glyph from the Loader's frame (single clock, already partially done per CHANGELOG #4353 `sharedSpinnerFrame`), and only write the title when the *label/state* changes, not every frame; or
- Drop the title-separator animation entirely and keep only the static `π : label` / `π > label` separators, relying on the in-TUI spinner for motion feedback.

### Fix D — Ensure `working` state returns to `idle` promptly

The profile shows 45 s of sustained `working` with 79 ms of work. If the agent is genuinely idle (between turns, waiting on user), the title state should be `idle` and the Loader should be stopped. The `event-controller.ts` sets `setTerminalTitleState("idle")` at line 1287 on agent end, and `"working"` at 460/1154. If there's a long gap *within* a turn (e.g. LSP indexing, provider thinking), the spinner legitimately runs — but that's exactly when Fix A/B matter most. Worth auditing whether any code path leaves `working` set without a corresponding `idle` transition.

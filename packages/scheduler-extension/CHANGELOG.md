# Changelog

## [Unreleased]

### Added

- Initial release: session-quota-aware prompt queue (`/scheduler`) — queue prompts and drain them unattended across Claude 5-hour session windows, with provider rate-limit holds (429 retry-after), network-outage backoff probing, a self-healing watchdog, pause-on-user-abort, resume-not-skip semantics, crash recovery, and `/scheduler export`.
- `/scheduler add-file` batch format: a file of comma-separated `{prompt: "..."}` objects (whitespace/newline tolerant, bare or quoted keys, optional `[...]`, trailing comma ok) queues up to 30 tasks atomically; syntax/shape errors queue nothing and name the offending entry. Plain-text files still queue as one prompt.
- `/scheduler add-file` verbatim batch format: a file starting with an `@@prompts` header splits into prompts on `---` separator lines and takes each prompt body **exactly as written** — no escaping of quotes, back/forward slashes, newlines, JSON, or pasted code. Pick a custom boundary with `@@prompts sep=<token>` (heredoc/MIME-boundary style) when prompts contain the default separator. Leading/trailing/doubled separators are ignored; still capped at 30 and queued atomically. The legacy JSON `{prompt: "..."}` batch remains supported as a fallback, and files without a header still queue as one prompt.
- Content-policy ("cyber") violation recovery: when a turn is rejected by Anthropic's usage-policy classifier, the poisoned conversation is purged with a fresh context (`ctx.newSession`, `compact` fallback) before the task is re-dispatched with the resume preamble, and the attempt is refunded so a poison cascade never burns the `maxAttempts` budget. A new `maxContextResets` config (default 5) fails a prompt that trips the classifier even in a clean context instead of looping forever. Logged as a `context_reset` event.
- Self-describing diagnostic logging: every `end` record now carries the turn `classification` (`rate_limit` / `outage` / `content_policy` / `user_abort` / `task_fault` / `stalled` / `shutdown`), whether the attempt was `refunded` vs counted, the `attempts`/`maxAttempts` budget, a `terminal` flag with the exact `/scheduler retry <id>` recovery hint, and a truncated `prompt`. `dispatch` records carry the prompt and attempt budget too. `/scheduler log` renders these inline (e.g. `end t2 failed task_fault counted attempts=3/3 TERMINAL » …`), so "why did it fail and will it retry?" is answerable from the log alone — no opening `state.json` or reading the source classifiers.
- Prompt-hash tracking + outcome ledger: every task carries a stable `promptHash` (SHA-256/12 of the prompt, backfilled for existing tasks) so the same prompt is traceable across runs and re-queues. After every pass/fail the scheduler regenerates a human-readable table at `task-ledger.md` — `hash | status | prompt (≤100) | summary (≤100)` — where the summary is generated purely by code (the turn's own final assistant line for a pass, or `classification: error` otherwise), never an extra LLM call. View it with `/scheduler ledger`; `promptHash` and `summary` are also stamped on `end` log records.

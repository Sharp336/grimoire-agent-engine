Outlines, finds, and edits code symbols by name via native tree-sitter (no language server).

<instruction>
- `action: "overview"` — outline the symbols (name, kind, line, nesting) in a file or small file scope. Use to map a file's structure before editing, or to confirm where a symbol lives
- `action: "find"` — locate symbols by `name` across a path scope (file, directory, or glob). Within a scope of up to 200 files `find` scans exhaustively and never misses a symbol `overview` would show; for larger scopes it uses a fast content prefilter that skips files over ~4MiB (rare — narrow the scope, or run `overview` on the specific file). Optional `kind` and `container` filter the candidate set after outlining — they narrow results, they are not limited to `manipulate` disambiguation
- `action: "manipulate"` — replace, delete, or insert relative to a named symbol (`op`: `replace`/`delete`/`insert_before`/`insert_after`; `text` is the payload for `replace`/`insert_before`/`insert_after`). It previews the edit as a diff and stages it; call `resolve` to apply or discard (like `ast_edit`). `replace`'s `text` overwrites the whole construct, including any attached decorators/attributes, and must carry correct indentation
- **Preferred handoff:** after `overview` or `find`, pass the emitted `selector` to `manipulate` instead of reconstructing `path`, `name`, and disambiguators by hand — the selector embeds the source address and structural identity so `manipulate` decodes it before scope resolution. A stale or ambiguous selector fails closed; fall back to name-addressing when that happens
- **Name-addressed manipulate:** pass `name` and `path` (required — the single target file) for `manipulate`; `path` defaults to `.` for `find`/`overview`. When a `name` is non-unique in the target file, narrow with `kind` (the raw domain kind string the outline emits, e.g. `function`/`method`/`class`/`trait`/`struct`), `container` (enclosing type name — a Rust `impl`/`trait` or a Go receiver type), or `line` (the symbol's `selectionLine`). Run `find` (or `overview`) first to read the candidates, then `manipulate` with the disambiguator for the one you want. Selector mode is the only way to omit `path`
- `symbol` is a LIGHTER alternative to `ast_grep`/`ast_edit` (no AST patterns — address by name, not by structural template) and to `lsp` (no running language server). Reach for it for quick "where is X / what's in this file" work; reach for `ast_grep` when syntax shape matters and `lsp` when you need cross-file references or rename refactors
</instruction>

<output>
- `overview`: per file, a header `<relpath> — <count> symbol(s)` then pre-order lines `<indent><kind> <name>[ <detail>] @ line <selectionLine>[ selector=<value>]` (indent = nesting depth). Each uniquely addressable symbol appends `selector=sym:v1:<encoded>`; byte-identical duplicates append `selector=ambiguous` instead; symbols inside an internal-URL-backed directory scope whose provenance cannot be preserved append `selector=internal` — for `ambiguous` or `internal`, fall back to name-addressing with `line` (they are not selector-addressable). Empty file or parse error → `<relpath> — no symbols (empty file or parse error)`
- `find`: flat lines `<kind> <name>[ (<container>)] @ <relpath>:<selectionLine>[ selector=<value>]`, prefixed by `Found <n> symbol(s) matching "<name>":`. Exact name matches are preferred; case-insensitive substring is the fallback only when no symbol matches exactly. Paginate with `skip`/`limit`; truncation appends `… <m> more; pass skip=<skip+limit>`. No match → `No symbols found.`
- `manipulate`: a diff preview of the staged edit. `resolve` applies it (returning a fresh `[<relpath>#<tag>]`) or discards it; the edit routes through the same pipeline as `edit` (plan-mode read-only, stale-tag validation, LSP write-through)
</output>

<critical>
- `find` matches the symbol `name` only — exact matches when any exist, otherwise case-insensitive substring — and lists every match. `kind` and `container` filter the candidate set after outlining, narrowing results before exact-vs-substring selection; they are not `manipulate`-only disambiguators
- Prefer the `selector` from `find`/`overview` results when calling `manipulate` — it embeds the source address, language, and structural identity so you skip reconstructing `path`, `name`, and disambiguators by hand
- Selector-addressed `manipulate` decodes the selector before scope resolution; stale or ambiguous selectors fail closed, so fall back to name-addressing with explicit `path`/`name`/disambiguators
- A scope too large to outline safely (>50 files for `overview`, >200 candidate files for `find`) errors rather than silently truncating — narrow the path/glob or use a more specific name
</critical>
